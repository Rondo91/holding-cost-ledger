# 信息架构与交互流程

> 由 `site/index.html`、`site/design.html`、`assets/js/app.js` 与埋点实现反推整理。
> 原始事实来源是代码本身；若冲突，以代码为准。

---

## 一、站点结构（两个独立 HTML，无路由）

```
持有成本账本
├── index.html   工具页（默认落地页，即时计算）
└── design.html  设计说明页（可单独分享直达）
```

- 导航：顶栏「工具 / 设计说明」，`aria-current` 标注当前页。
- 决策原因（CHANGELOG v1.0）：工具要保状态即时算，说明页要能被单独分享直达，所以不用单页 hash 路由。
- 两页共享：`topbar`、`footer`（footer 含完整隐私声明 + 跳设计说明链接）。

## 二、工具页分区（自上而下）

| 分区 | id | 内容 | 出现时机 |
|---|---|---|---|
| A 输入 | `#sec-input` | H1 + 副标题 + **回看提示条 `#recall-banner`** + OCR 卡片 + 表单（设备名称选填 / **设备品类选填** / 购买日期必填 / 实付金额必填） | 始终（回看条仅回看时出现） |
| B 基础结果 | `#sec-base` | 当前持有成本（日均购置成本主数字 + 已持有天数 + 已投入金额）+ **记入账本 `#save-row`** + **衰减曲线 `#curve-body`** + 残值引导区（`#residual-body` / `#residual-form`）+ **参考锚点 `#anchor-slot`** | 两个必填项齐全 + 输入停稳后出现 |
| C 完整结果 | `#sec-full` | 扣除残值后（净持有支出 / 日均净支出 / 回收率） | 残值填入后 |
| **D 我的账本** | `#sec-history` | 排行（≥2 台）+ 列表 + 隐私说明 + 导出 / 清空 | **有记录才显示**；无记录整节隐藏 |
| 弱层级 | `#formula-details` | 计算口径、公式与假设（`<details>` 默认收起） | 有基础结果即可展开 |
| 反馈入口 | `#feedback-entry` | 「这两个数字对你有用吗」按钮 | 完整结果后 |
| 弹层 | `#feedback` | 两问反馈（`role="dialog"`，`aria-modal`） | 点入口后 |

**两个新增块的层级原则**：

- 曲线与锚点都用 `<details>`，与公式块同层级——它们是**解释与旁证**，不是结果。
  曲线的**结论句写在 `<summary>` 上**：点开只是看形状，不点开也能拿到答案。
- 账本排在完整结果与反馈之后：先拿到数字，再谈记录。

**重绘保护**：曲线与锚点用 `dataset.sig`（价格 + 天数 + 品类）比对，
签名不变就不重画——否则每次输入都会重设 `innerHTML`，把用户已经展开的 `<details>` 合上。

## 三、核心交互流

```
进入 → page_view
  │
  ├─（可选）上传订单截图 → ocr_upload_started → ocr_result
  │      └─ 逐项确认 → ocr_field_confirmed（每个字段一条）
  │
  ├─ 首次聚焦任一字段 → input_started
  ├─ 每个字段填完（停稳 900ms / 失焦）→ field_completed
  │
  ├─ 两必填项齐 + 停稳 → 基础结果出现 → residual_prompt_shown → base_result_viewed
  │     ├─ 品类可推断 → 锚点渲染 → benchmark_hint_shown（展开 → benchmark_hint_expanded）
  │     ├─ 展开衰减曲线 → curve_expanded
  │     └─ 点「记入账本」→ history_saved（即时上报）→ 账本区出现 → history_viewed
  │
  ├─ 残值三选一：
  │    ├─ 填二手价（一个价格/价格区间）→ residual_entered → 完整结果 → full_result_viewed
  │    └─ 暂时不需要 → residual_skipped（明确显示「未计入残值」，不显示 0 元）
  │
  ├─ 展开公式 → formula_expanded / 收起 → formula_collapsed
  │
  ├─ 反馈两问 → feedback_opened → feedback_answered
  │     问1：有帮助 / 没有帮助 / 说不上来
  │     问2：继续用 / 去查二手价 / 卖掉 / 换新 / 暂时不确定
  │
  └─ 账本区（v2.0）
       ├─ 回看 → 回填表单 + 顶部提示条 → history_recall（「退出回看」清空表单）
       ├─ 删除 → 按钮原地变「确认删除？」，3 秒内再点生效 → history_deleted(reason=single)
       ├─ 清空 → 行内确认条 → history_deleted(reason=clear_all)
       └─ 导出 → Blob 下载 JSON → history_exported
```

**账本的三条交互约定**：

1. **手动点击才记入**，不自动保存——自动保存会把"随便试算一下"也写进账本，
   也会把隐私承诺从"你主动存的"放宽成"算过的都在浏览器里"。
2. **判重键 = 设备名 + 购买日期 + 实付金额**，三者一致视为同一台设备 → 更新不新增
   （补填二手价后再点一次，就是更新同一条）。
3. **数字按今天重算**：列表与排行都用打开当天的日期算，快照只做「上次 ¥X/天 → 今天 ¥Y/天」对比。
   按快照排行等于拿不同日期的数字比大小。

### 双时间线设计（v1.1 引入）

- **视觉线（200ms 防抖）**：输入过程中数字实时重算重画。
- **判定线（900ms 停稳或失焦）**：结果区首次出现 + 全部漏斗埋点，只在停稳后发生。
- 遗留：输入中间停顿超 900ms 仍会被记为一次完成（已写进设计说明页）。

### 埋点上报策略（analytics.js）

- `MILESTONE_EVENTS`（即时上报）：`page_view`、`input_started`、`base_result_viewed`、`full_result_viewed`、`feedback_answered`、**`history_saved`（v2.0 加入）**。
  - `history_saved` 进即时名单的理由与 v1.1 一致：它是 v2.0 的核心转化动作，
    页面一关就丢会**低估**账本记入率——偏差方向偏保守，但同样是错的。
- 其余事件攒批上报 → **记录时间晚于真实发生时间**（v1.1 修复的原因）。
- 已知副作用（2026-09-30 数据核实）：`residual_entered` **不在**即时名单里，数据中它排在 `full_result_viewed` 之后，顺序倒置是攒批所致，不是用户行为颠倒。
- v2.0 的 `step` 枚举新增 `history`：历史动作发生在完整结果之后，是独立阶段，
  塞进 `full` 会污染既有漏斗口径。

## 四、AI（截图识别）职责边界

- 模型只做**字段识别**（设备名称/下单日期/实付金额），**算术永远由纯函数完成**。
- 选型：`rankVisionModels()` 按"非推理优先"排序，一次最多尝试 2 个候选，只对 `call_failed`/`parse_failed` 重试。
- 截图**不上传存储**：浏览器内读成 data URL 直接交给模型。
- 识别结果必须**逐项确认**才写入表单；不确定字段标「待确认」。
- v1.3 起记录 `model` 与 `duration_ms`（客户端实测耗时）。
- **v2.0 起逐次记录**：`ocr_attempt`（attempt 序号 / model / 该次 duration_ms / 该次 status）。
  原因：v1.3 的总时长 + 最终模型让"失败的那次尝试"在数据里隐形，
  「换模型重试有没有变快」无法回答。`ocr_result` 语义不变，两条时间线并存可交叉校验。
- v2.0 补上：识别确认填入后也会触发 `field_completed`——
  原本走识别这条路的用户在漏斗里是空白的，好像他们从来没完成过输入。
- **参考数据不经过模型**：品类推断是关键词规则（最长命中优先，可单测），
  参考区间是人核过出处后硬编码的静态数据（见 PRD §6.1）。

## 五、隐私架构（信息架构的一部分）

- 无登录、无身份字段；金额/日期/回收率只上报**区间**（band）。
- 两张表 `calc_events` / `calc_feedback`：RLS 开启，仅 INSERT 策略，无 SELECT 策略，无派生视图。
- 数据保留策略：暂无（量大了需定）。

### v2.0 新增：本地账本的存储边界

| 键 | 用途 | 生命周期 |
|---|---|---|
| `hcb_history` | 用户主动记入的账本记录（schema version 2，软上限 200 条） | 持久，直到用户清空或清浏览器数据 |
| `hcb_history_corrupt` | 损坏数据的原文留档 | 损坏时写入，不自动清理 |
| `hcb_session_id` | 匿名会话标识 | sessionStorage，关标签页失效 |
| `hcb_ocr_attempts` | 识别次数计数 | sessionStorage |

四条设计约束：

1. **没有任何上传路径**——`history-store.js` 只认注入进来的 storage 接口，
   `app.js` 传的是 localStorage 适配层；代码里不存在把账本发出去的调用。
2. **软上限 200 条时拒绝新增并提示先导出**，绝不自动删旧记录。
3. **更高 schema 版本只读不写**，防止页面回滚把数据写坏。
4. **共用电脑可见这条明说在界面上**，不加密码（假的安全感比没有安全感更糟）。

## 五·补、发布工程：静态资源版本号

浏览器缓存会让老访客拿到**新 HTML + 旧 JS**（表现为"有品类框但没选项、没有记账按钮"）。
因此入口资源与**被改动模块的 import 路径**都带 `?v=2.0.0`，发版 bump。
只给入口加版本号不够：旧 `analytics.js` 的白名单不认 `history_saved`，事件会被数据库静默拒收。

## 六、实测核验记录

### 2026-09-30（v1.x，本地 + Chrome headless）

- 桌面 1280 / 移动 390 两档全流程走通：输入 → 基础结果（¥4.50/天，1,112 天）→ 残值 ¥2,200 → 完整结果（净支出 ¥2,799；移动端 ¥2.52/天、回收率 44.0%）→ 公式展开 → 反馈弹层。计算结果与手工核算一致。
- 控制台唯一错误：`/favicon.ico` 404（无 favicon 文件，无功能影响）。
- 发现缺陷：**「价格区间」输入框在「一个价格」模式下不隐藏**（`.range-inputs` 的 `display:flex` 覆盖 `[hidden]`），详见《视觉规范-DesignTokens.md》末节。
- 截图存于 `交付物/实测截图/`（10 张，桌面+移动、两页覆盖）。

### 2026-10-09（v2.0，本地 HTTP + 线上域名，headless Chrome + CDP）

- **单元测试 133 个全过**（10 个测试文件，`node --test` 逐文件；Windows 下不能写 `node --test tests/`）。
- 线上 `https://holding-cost-ledger.app.workbuddy.host/`：`__hcbEvents.mode()` 返回 `cloud`；
  品类下拉 8 个选项可选；选「手机」+ 持有 9 个月 → 锚点给出 42.0% – 78.0% 与折算金额；
  记入账本 → 账本区出现；补二手价后再点 → 提示"已更新这条记录"。**控制台零报错。**
- 锚点三态实测：有数据（手机 1 年以内）/ 年限超出统计范围（3 年以上 → 显示"没有"）/ 品类无数据（耳机）文案与来源标注均正确。
- 账本全流程：记入 → 排行（2 台）→ 回看（回填 + 提示条）→ 退出回看（清空）→ 删除两步确认 → 导出下载 → 清空确认条可见。
- 数据库：9 个新事件全部实测插入成功（含 `category` / `attempt` 新字段）后删除验证记录。
- **发布后发现的唯一问题**：用户端表现为"品类选不了、没有记账入口"——
  **浏览器缓存了 v2.0 之前的 JS**，不是功能缺陷。已加静态资源版本号并复验通过。
