# 持有成本账本 · 产品需求文档（PRD）

| 项目 | 内容 |
|---|---|
| 产品名称 | 持有成本账本 |
| 版本 | **v2.0**（2026-10-09） |
| 文档状态 | 定稿（v1.0 部分保留原样，v2.0 内容以「v2.0」标注，便于对照看演进） |
| 一句话定位 | 帮用户在出售或更换电子设备前，算清这台设备每天的持有成本和现在的价值回收情况，**并把算过的结果留成一本可以继续记的账** |

### 版本记录

| 版本 | 主题 | 一句话 |
|---|---|---|
| v1.0 | 算清一台设备 | 两个必填项 → 日均购置成本；补一个二手价 → 净持有成本与回收率 |
| v1.1 | 测量可信 | 埋点抓出"输到一半被记成完成"，拆开视觉线与判定线 |
| v1.5–v1.7 | 设计评审落地 | 可达性、视觉层级、反馈入口可见性 |
| **v2.0** | **从计算器变成账本** | 记下多台设备 + 给二手价一个参考锚点 + 画出衰减曲线 + 修掉 OCR 的测量盲区 |

> **为什么 v1.0 叫「账本」却只能算一次，是个要承认的问题。**
> 名字承诺了"可积累"，行为却是一次性的——刷新即忘。v2.0 补上记录能力，
> 不是加功能，是把名字兑成真的。

## 1. 背景与目标

### 1.1 要解决的问题

用户在考虑卖掉或换掉一台电子设备时，手上有两个信息是缺失或模糊的：

1. **这台设备到目前为止让我花了多少钱**——多数人记不清当初的实付金额，更不会去算分摊到每天的成本。
2. **现在还值多少**——能查到行情，但挂牌价和实际成交价差距大，且这个数字单独看没有决策意义。

缺的不是数据，是**把两个数字放在一起的那个视角**。

### 1.2 首版要拿到的结果

用户在不注册、不查任何外部资料的前提下，填两个字段（购买日期、实付金额）就能拿到第一个有效数字；
如果愿意再补一个数字（当前二手价），得到一个完整的成本结论。

### 1.3 不追求的目标

- 不追求用户量、留存、商业化
- 不追求功能完整
- 不追求"帮用户做决定"——只提供算清楚的事实

### 1.4 v2.0 要解决的三个新问题（上线后暴露出来的）

前两个是 v1.0 自己留下的洞，第三个是测量工具的洞。

1. **"二手价我不知道填多少"** —— 取舍②为了不逼用户编数字，把残值做成软引导；
   但"可跳过"不等于"会填"，而**不知道填多少**和**不想填**是两件事。
   v1.0 只解决了后者（给了"暂时不需要"），前者一直没人管，于是用户要么放弃、要么随手写一个。
   → v2.0：给行业参考区间锚点（品类 × 持有年限段），并写清口径差异。
2. **算完就忘，一台设备要重填一遍** —— 用户有多台设备时，每次都要从头输入，
   而且"哪台最烧钱"这个天然的比较需求完全没被接住。
   → v2.0：本地账本（记录 / 回看 / 排行 / 导出）。
3. **"换模型重试到底有没有变快"没有数据回答** —— v1.3 记了总时长和最终模型，
   失败的那次尝试在数据里是隐形的（见 §6.3）。
   → v2.0：OCR 按次测量。

### 1.5 v2.0 依然不追求的目标

- 不做云同步（需要登录，会推翻取舍④，见 §7）
- 不做估价、不做"一键填入"
- 不因为有了账本就去算"维修/配件"——那会改动全部口径，是另一个量级的决策（见 §3.3）

## 2. 目标用户与场景

**服务的人群**：犹豫是否更换电子产品、或考虑出售旧设备，并且关心电子产品使用成本的人。

**典型场景**：用户正在二手平台看同款设备的行情，或在电商订单页确认当初花了多少钱，
此时想快速知道"这台设备每天花了我多少、现在卖掉相当于回收了多少"。

**场景的三个约束（直接决定设计）**：

1. 大概率在手机上发生 → 移动端优先
2. 决策窗口很短，用户不愿填表 → 必填项压到 2 个，输入即出结果
3. 手边可能没有准确数字 → 必须允许跳过、允许填区间、允许用截图识别补全

## 3. 需求范围

### 3.1 P0（首版必须交付）

| # | 需求 | 验收标准 |
|---|---|---|
| P0-1 | 设备名称或类型 | 选填；≤ 60 字；不填不影响任何计算 |
| P0-2 | 购买日期 | 必填；不接受未来日期；不接受不存在日期（如 2 月 31 日）；早于 25 年前时提示确认而非拦截 |
| P0-3 | 实际支付金额 | 必填；> 0；支持千分位与货币符号输入；失焦时回填千分位；> 200000 时提示确认 |
| P0-4 | 当前预计二手价 | 选填；支持单个价格与价格区间两种填法；可随时跳过；区间下限 > 上限时报错 |
| P0-5 | 日均购置成本 | 两个必填项齐全后**立即**出现，无需点击任何按钮 |
| P0-6 | 净持有成本与回收率 | 补充二手价后立即出现；未补充时明确说明"未计入残值"，**不显示 0 元** |
| P0-7 | 公式、口径与假设 | 可展开查看，默认收起；不占据主视线 |
| P0-8 | 输入错误与异常状态 | 每个字段独立报错；错误与提示分级（错误拦截、提示不拦截） |
| P0-9 | 反馈入口 | 两个问题：结果是否帮助判断下一步 / 接下来更可能做什么 |
| P0-10 | 订单截图识别 | 上传截图 → 识别字段 → **逐项人工确认** → 才填入计算；不确定字段标"待确认" |
| P0-11 | AI 不可用时的降级 | 识别不可用时隐藏入口并说明原因，纯手动路径完整可用 |

### 3.1b P0（v2.0 新增）

| # | 需求 | 验收标准 |
|---|---|---|
| P0-12 | 设备品类 | 选填，默认"自动识别"；按设备名称关键词推断并在下方说明依据；**识别错了只影响参考区间是否出现，不影响任何计算**；可随时手动改 |
| P0-13 | 参考回收率锚点 | 按「品类 × 持有年限段」展示行业区间 + 按实付折算的金额区间；**必须同时展示来源、数据时间与口径差异声明**；查不到可靠来源的品类显示"暂无可靠参考"；持有超过统计年限（3 年）同样显示"没有" |
| P0-14 | 锚点不代填 | 只给区间，**不提供一键填入**，不自动写进输入框 |
| P0-15 | 记入账本 | 用户**主动点击**才写一条；同名+同日期+同金额视为同一台设备 → 更新而非新增；写入成功给出明确回执 |
| P0-16 | 账本区 | 列表（按今日日均）+ ≥2 台时的日均排行 + 回看（回填表单）+ 单条删除（两步确认）+ 清空（行内确认）+ 导出 JSON 备份；**无记录时整节隐藏** |
| P0-17 | 日均衰减曲线 | 结论句直接写在可展开块的标题行（不点开也能拿到答案）；展开后是内联 SVG；固定声明"摊分数学 ≠ 继续持有更划算，不构成建议" |
| P0-18 | OCR 按次测量 | 每次模型尝试单独上报（序号 / 模型 / 该次耗时 / 该次结果）；原 `ocr_result` 语义不变 |
| P0-19 | 账本容错 | JSON 损坏 → 原文隔离留档后重置；配额耗尽 → 提示"没记上"且不打断主流程；更高 schema 版本 → 只读不写；软上限 200 条 → 拒绝新增并提示先导出，**绝不自动删旧记录** |

### 3.2 P1（v2.0 仍不做，理由另附）

| 不做 | 为什么现在不做 |
|---|---|
| 跨设备云同步 | 需要登录，直接推翻取舍④；且账本数据比一次性计算敏感得多（见 §7.4） |
| 把维修 / 配件 / 以旧换新补贴计入持有成本 | 会改动全部口径与指标定义，属于"另一个量级的决策"；要做就单独开一版 |
| 用用户自己的历史做个性化参考（"你上一台 iPhone 两年回收 52%"） | 冷启动没有数据；先有账本、再有个性化，顺序不能倒 |
| 价格来源链接与查询日期记录 | 与"不自动搜价"一致；锚点已给出处，够用 |
| 设备名称的自动补全与规格识别 | 品类推断已覆盖锚点所需；再往下是过度设计 |

> 注：v1.0 的 P1 里「多台设备记录与对比」「历史成本曲线」**已在 v2.0 落地**；
> 「曲线」落地为**日均衰减曲线**（P ÷ D 随天数下降），不是"历史价格走势"——
> 走走势图需要外部行情数据，那又回到"自动搜价"那条不做的路上。

### 3.3 明确不做

| 不做的事 | 理由 |
|---|---|
| AI 推荐"应该卖"或"继续用" | 这是建议，不是算账。给建议会把可信工具变成讲不清依据的黑箱 |
| AI 自动联网搜索当日最新二手价 | 数据源不稳定、不可解释，且用户自己查一遍只要 30 秒。**此条仅指"实时联网抓取"**，与 §5.5 的行业参考区间不是一回事——后者是人工核对出处后硬编码的静态表（不联网、不实时、不针对具体设备、不可代填） |
| **用 AI 生成参考回收率** | 模型给的数字不可复现、无出处，等于用一个看起来有依据的假数字替换用户自己编的数字——**比不干预更糟** |
| **锚点一键填入** | 代填出来的价格，到底是用户的判断还是我的判断？取舍②说"编造的价格比没有价格更糟"，代填是同一件事的变体 |
| **云同步账本（需登录）** | 为同步而引入账号，是把隐私承诺换成一个便利功能，不值 |
| **给查不到数据的品类拍一个"合理"的区间** | 编数一次，整个工具的可信度就归零；宁可显示"没有" |
| 判断耐用度、性价比 | 与"算清成本"无关，属于另一类问题 |
| 账号体系、登录注册 | 整个流程不需要身份，加登录只会增加流失 |
| 收集订单号、姓名、地址、手机号 | 计算完全用不到 |

## 4. 用户流程

```
输入（设备名称 · 设备品类[选填/自动识别] · 购买日期 · 实付金额）
  ↓ 两个必填项齐全即触发，无按钮
基础结果（已持有天数 · 已投入金额 · 日均购置成本）
  ├─ 记入账本 ← 用户主动点击，随时可点（补填残值后再点即更新同一条）
  ├─ 日均衰减曲线（可展开，结论句写在标题行）
  ↓ 软引导，可跳过
补充残值（当前二手价，支持区间）
  │   └─ 不知道填多少？← 行业参考区间锚点（只展示，不代填）
  ↓
完整结果（净持有支出 · 日均净持有支出 · 按实付回收率）
  ↓
反馈（两问）
  ↓
我的账本（列表 · 排行 · 回看 · 删除 · 清空 · 导出）← v2.0 新增分区
```

**流程设计上的一个关键判断**：把"买价"放在必经第一步，尽管访谈显示只有 3/12 的用户关心它。

理由：只做二手价查询，这个产品就是闲鱼的一个劣化版，用户没有理由用。二手价是用户本来就在查的东西——顺着他的既有行为接住他；持有成本是他查不到也算不清的东西——这才是差异化的价值所在。

代价是第一步的欲望强度偏低，因此"必填项压到 2 个""输入即出结果"是硬约束，不是体验优化。

### 4.1 v2.0 流程上的四个判断

1. **账本放在结果之后，不放在输入之前。** 先让他拿到数字，再问要不要记下来——
   还没看到结果就要用户"建档"，是把留存成本前置到转化之前。
2. **手动点击才记入，不自动保存。** 自动保存会把"随便试算一下"也写进账本；
   更重要的是它会把隐私承诺从"你主动存的"放宽成"算过的都在浏览器里"（见 §7.4）。
3. **账本区无记录时整节隐藏。** 首访用户看到一块空账本只会困惑；
   它应该在用户第一次点"记入账本"之后出现，而不是提前占位置。
4. **锚点紧贴"填二手价"那一步的下方**（表单展开或收起都在），而不是放到结果区。
   用户是在这一步卡住的，参考信息就该在卡住的地方给，
   不是等他填完了再告诉他"你填得偏高"——那是事后评判，不是帮忙。

## 5. 计算口径

> 这是全文档中最不可随意变更的部分。口径一旦漂移，同一个输入会得到不同结果，工具的可信度即刻归零。

### 5.1 字段定义

| 符号 | 字段 | 定义 |
|---|---|---|
| P | 实际支付金额 | 购买时实际支付的金额，已扣优惠，不含订单中的其他商品 |
| S | 当前预计二手价 | 现在出售预计能收到的金额。建议填同款近期实际成交价，而非平台挂牌价 |
| D | 持有天数 | 从购买日期到计算日期的自然日数 |
| T | 计算日期 | 默认是打开页面的当天 |

### 5.2 公式

```
D = max(1, T − 购买日期 + 1)        自然日，含购买当天；当天买入记为 1 天
已投入金额      = P
日均购置成本    = P ÷ D
估算净持有支出  = P − S
日均净持有支出  = (P − S) ÷ D
按实付回收率    = S ÷ P
```

### 5.3 区间形态

用户填写价格区间 `[a, b]` 时：

```
净持有支出 = [P − b, P − a]
日均净支出 = [(P − b) ÷ D, (P − a) ÷ D]
回收率     = [a ÷ P, b ÷ P]
```

### 5.4 必须守住的四条行为约定（第 4 条为 v2.0 新增）

1. **S 为空 → 只显示日均购置成本**，明确说明"未计入残值"。
   不显示净持有支出、日均净支出、回收率。**显示 0 元会被读成"这台设备已经一文不值"。**
2. **S > P → 净额为负是正常结果**（以旧换新、设备升值、溢价出手），
   文案改写为"已回本，净收益"，不把负号原样抛给用户。
3. **区间跨越回本点 → 明确提示**"这个区间跨越了回本点"，并引导收窄区间。
4. **（v2.0）账本里的数字一律按"今天的日期"重算，按记录当天的快照只做对比提示。**
   账本的心智是"每天翻开，数字是今天的"。各条记录的快照日期不同，
   按快照互相比较（尤其是排行）等于拿不同日期的数字比大小，没有意义。
   快照唯一的用途是一句对比：「上次 ¥4.07/天 → 今天 ¥3.86/天」。
   **代价：数字每次打开都会变。这是"按天摊分"口径的固有属性，界面上明说，不藏。**

### 5.5 参考回收率的口径（v2.0，与计算口径同等严肃）

参考锚点不是"计算"，是"旁证"，因此它的口径必须单独写清，否则旁证会变成误导。

**为什么要给旁证**：只给一个回收率百分数，用户拿到的是孤立数字——"我这台用了两年、回收 45%，这算好还是不好？"
锚点回答的正是这句话：这个品类在这个持有年限段，行业大致落在哪个区间。它给的是**参照系**，不是"你这台值多少"。

| 项 | 规则 |
|---|---|
| 形态 | 品类 × 持有年限段 → 区间 `[lo, hi]`，不是单一数字 |
| 年限分段 | 1 年以内 / 1–2 年 / 2–3 年 / 3 年以上。保值率随年限陡降，单一数字会把"3 个月"和"3 年"混为一谈 |
| 折算 | 按用户的实付金额折算金额区间；实付缺失时不给折算 |
| 口径差异（必须展示） | 行业保值率多按**发售价**统计、且多来自**回收商报价**（低于个人成交价）；本工具回收率按**实付**算。买得便宜会被低估，反之高估 |
| 来源与时间 | 每个品类单独标注来源与数据时间，界面原样展示 |
| 无数据时 | 显示"暂无可靠的公开参考数据"；**不得用相邻段顶替，不得拍脑袋填** |
| 不做什么 | 不代填、不当估价、不因为有了锚点就改任何一条计算口径 |

## 6. AI 与程序的职责边界

这是本产品对 AI 能力最核心的一条设计约束。

| 环节 | 负责方 | 说明 |
|---|---|---|
| 从订单截图提取字段 | AI | 设备名称、下单日期、实付金额、来源平台 |
| 判断字段是否可靠 | AI + 用户 | 模型自己没把握的字段标"待确认" |
| 确认字段是否可以进入计算 | **用户** | 必须逐项确认后点"确认并填入" |
| 一切算术 | **程序** | 纯函数，无副作用，可单测 |

三条硬规则：

1. **识别结果在用户确认前不参与任何计算。**
2. **计算口径必须稳定可解释**——同样的输入必须得到同样的输出，所以算术永远不交给模型。
3. **模型输出是不可信输入**——它只被填进表单，由用户确认，绝不直接进入计算链路。

**降级路径**（任一条触发都不影响主流程）：

| 触发 | 行为 |
|---|---|
| 模型服务未接入 / 无可用多模态模型 | 隐藏上传入口，说明原因，引导手动填写 |
| 调用失败或超时 | 提示重试，同时明确引导手动填写 |
| 返回内容无法解析 | 提示识别失败，转手动 |
| 用户主动放弃识别 | 直接手动，全程无差别 |

### 6.1 v2.0 补充：参考数据不是 AI 的产物

参考回收率是**人核过出处之后硬编码进前端的静态数据**，不是模型生成、不是实时接口。
理由与 §3.3「不让 AI 生成参考值」一致：**没有出处和时间的数字，本质上是编的**，
只是编得更像真的。品类推断用关键词规则（可单测、可复现），同样不交给模型——
它只需要"认出一个品类"，不需要智能。

### 6.2 v2.0 补充：AI 环节必须能被测量

"读"这件事也要留证据：识别用了哪个模型、每次尝试各花了多久。
没有这两个字段，只能靠人肉读屏幕，也就谈不上优化。

### 6.3 v1.3 遗留、v2.0 修掉的测量洞

`ocr_result.duration_ms` 记的是**整次识别的总时长**，`model` 记的是**最终生效的模型**——
失败的那次尝试在数据里完全不可见。于是"换模型重试有没有变快"这个问题没有数据能回答
（首次实测 18.2 秒，看不出两个模型各占多少）。

修法：新增 `ocr_attempt`（逐次记：序号 / 模型 / 该次耗时 / 该次结果），
**`ocr_result` 一个字段都不改**——两条时间线并存，可交叉校验（总时长 ≈ 各次之和 + 重试间隙），
历史数据零迁移。

## 7. 数据与隐私

### 7.1 收集原则

只收集计算与验证所必需的字段；不收集姓名、地址、手机号、订单号。

### 7.2 实现层面的保证（而非口头承诺）

| 承诺 | 实现方式 |
|---|---|
| 截图不上传 | 只在浏览器内读成图片数据，直接交给模型，不经过任何存储 |
| 不记录用户填写的数值 | 埋点只上报金额 / 天数 / 回收率所属**区间**，不上报原文 |
| 不收集身份信息 | 数据库表中不存在这些字段 |
| 写入受限于白名单 | 用数据库层 CHECK 约束把允许的字段名钉死，应用层写错也会被拒 |
| 统计无法被反向读取 | 埋点表只开放写入，不开放任何读取策略 |
| **（v2.0）账本数据不出浏览器** | 写入 `localStorage`，**没有任何上传路径**；平台不提供匿名登录，所以"顺手同步"在实现上也不存在 |

### 7.3 v2.0：隐私承诺的精确化（而不是放宽）

v1.0 写的是"不保存你填的数字"。这句话有个瑕疵——本地埋点缓冲本来就在用 `localStorage`。
v2.0 把它改成**可验证**的表述：

> 填入的数字不上传；**主动记入账本的记录只存在你的浏览器里**，不上传、不联网，可随时导出或一键清空。

范围收窄了，不是放宽了。三条配套：

1. **只有用户点了「记入账本」才写一条**，不自动保存。
2. **共用电脑可见这件事明说**，不加密码——假的安全感比没有安全感更糟。
3. **可退出**：一键清空 + 导出带走，不留"请联系我们删除"这种话。

### 7.5 v2.0：静态资源版本号（发布工程，不是产品功能）

浏览器缓存会让"老访客"拿到新 HTML + 旧 JS——表现为"有品类这个框但选不了、没有记账按钮"。
所以入口资源带 `?v=2.0.0`，**被改动过的模块其 import 路径也要带同一个版本号**：
只给入口加版本号不够，浏览器仍会拿缓存里的旧 `analytics.js`，而旧白名单不认 `history_saved`。
**每次发版 bump 版本号。**

## 8. 指标与验收

| 指标 | 定义 | 目标 | 性质 |
|---|---|---|---|
| 完整计算完成率 | 完成基础输入并看到结果 / 进入页面 | ≥ 60% | 漏斗地基 |
| 残值补充率 | 填写二手价 / 看到基础结果 | ≥ 40% | 意愿度量 |
| 中位完成时长 | 从开始输入到看到完整结果 | ≤ 60 秒 | 效率 |
| 决策帮助率 | 回答"有帮助" / 回答反馈总数 | ≥ 60% | 价值验证 |
| 结果页反馈率 | 留下反馈 / 看到完整结果（扣除残值后）；反馈入口只在完整结果后出现（v1.6 起） | ≥ 15% | 参与度 |
| 结果解释展开率 | 展开公式 / 到达结果页 | 仅观测 | **诊断项** |
| **（v2.0）账本记入率** | 记入账本 / 看到基础结果 | **仅观测** | 留存信号 |
| **（v2.0）账本回看率** | 回看 / 记入 | **仅观测** | 本地功能唯一的留存信号 |
| **（v2.0）锚点展开率** | 展开锚点 / 看到锚点 | **仅观测** | 诊断锚点形态是否有效 |

四条设计说明：

- **"结果解释展开率"不设目标。** 展开率高不等于产品好，可能恰恰说明默认解释没讲清楚。
  它的正确用途是诊断默认文案，而不是被考核。给诊断性指标设 KPI，只会逼着人把它刷上去。
- **反馈只问两问。** "你满意吗"几乎永远得到"满意"，且无法验证任何假设。
  换成"是否帮助判断下一步 + 接下来更可能做什么"，才能回答一个真问题：这些数字有没有真的改变用户的决定。
- **（v2.0）残值补充率的基线断裂了。** 口径没变，但软引导里多了参考锚点——
  影响用户决策的信息变了，所以 **v2.0 之后这个数与 v1.x 不能直接比较**。已经写在指标卡上。
- **（v2.0）三个新指标一律不设目标。** 账本和锚点都是新形态，先观测：
  如果锚点展开率极低，说明形态不对（可能该挪位置、也可能该给更窄的区间）；
  如果记入率极低，说明"算完就走"是真实需求，账本这个功能本身就该被质疑。
  **先有观测，再谈目标。**

## 9. 已知风险

| 风险 | 应对 |
|---|---|
| 用户记不清当初的实付金额 | 截图识别；允许跳到二手平台订单页核对；两个必填项已是下限 |
| 二手价由用户手填，误差大 | 支持区间输入；页面明确标注"估算"；引导填写成交价而非挂牌价 |
| 埋点在页面关闭时丢数据 | 关键漏斗节点立即上报；文档中说明真实指标为下界估计 |
| 样本量小时指标无统计意义 | 指标页同时展示样本量；样本量 < 30 时明确标注"仅作方向性参考" |
| 匿名写入的表被滥用 | 数据库层枚举约束 + 字段白名单 + 仅写不读 + 前端调用节流 |
| **（v2.0）参考数据存在系统性偏差** | 发售价口径 vs 实付口径、回收商报价 vs 个人成交价，两套来源未做跨源校准；**界面逐处标注来源与口径差异**，并在局限里写明"存在偏差"而不是"仅供参考"四个字糊过去 |
| **（v2.0）品类推断会误判** | 只影响锚点是否出现，**不影响任何计算**；界面说明"识别错了可以手动改"；误判代价被刻意限制在这一处 |
| **（v2.0）账本在本地，所以我看不到它** | 记入率、回看率只能靠事件计数，看不出用户记了几台、记了什么。这是取舍⑥的直接后果，已在局限里写明 |
| **（v2.0）缓存导致老访客拿到旧 JS** | 静态资源带版本号，改动过的模块 import 也带；发版 bump（见 §7.5） |
| **（v2.0）"数字每次打开都会变"可能被当成 bug** | 按天重算是刻意设计；界面明说，并写进设计说明页的口径解释 |

## 11. v2.0 的三组新取舍（承接第 4 节，详见 design.html 第 05 节）

| # | 冲突 | 选择 | 代价 |
|---|---|---|---|
| ⑤ | 参考锚点给得越具体越有用（最好一键填入） | 只给品类 × 年限的行业区间，附来源与口径差异，**不代填** | 用处远不如一键填入直观；区间还宽（手机一年 42%–78%），因为 iPhone 与安卓的真实差距就是这样 |
| ⑥ | 换设备就没了，云同步才像"账本" | 只写本地，不上传、不联网，配导出与清空 | 换设备/清缓存即丢；共用电脑可见——如实告知，不加密码 |
| ⑦ | 「再持有 23 天降到 ¥4 以内」读起来像一句建议 | 只画 P ÷ D 的摊分数学，固定声明"不构成持有建议" | 用户可能觉得"你都画出来了为什么不告诉我该不该卖"——这是故意留的缺口 |

**这三条的共同点：都用"少做一点"换"说得清"。**
锚点不代填是为了不制造假数据；账本不上云是为了不推翻隐私承诺；曲线不给建议是为了不越过产品边界。
v2.0 加了四个功能，但产品的边界没有向外扩一步。
